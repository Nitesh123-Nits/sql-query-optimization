How Query Planners Work
The mental model you need before optimizing anything

The query planner transforms your SQL into a physical execution plan using cost estimation. Understanding this pipeline is prerequisite knowledge — you cannot optimize a black box.

📝
Parse & Rewrite

SQL is parsed into a query tree. The rewriter applies rule-based transforms (views, rules). This stage is syntactic — no cost estimation yet.

📊
Statistics & Cardinality

The planner reads pg_statistic / information_schema. Stale stats = wrong plan. Run ANALYZE after bulk loads.

🔀
Plan Generation

All valid join orders & access methods are enumerated (up to join_collapse_limit). Each path gets a cost. The lowest-cost plan wins.

⚙️
Execution

The plan is executed via a pipeline of operators: SeqScan, IndexScan, Hash, Sort, Aggregate. Each has I/O and CPU cost components.

The Three Access Methods

MethodWhen UsedCost ProfileTip
Sequential ScanFull table scans, high selectivity queries (>10–20% rows)Low I/O per page, high total I/OOften correct for small tables — don't force an index scan
Index ScanLow selectivity (<5–10% rows), ordered output neededRandom I/O, high for large result setsB-tree default; use for range and equality predicates
Index-Only ScanAll projected columns are in the index (covering index)Zero heap access if VM is currentMost powerful optimization; design indexes to cover
Bitmap Heap ScanMedium selectivity; multi-index conditions via AND/ORBulk heap access sorted by blockPostgreSQL combines bitmap scans from multiple indexes
⚡ Key Insight
Random I/O (index scan on spinning disk) is 100–1000x slower than sequential I/O. On SSDs this gap narrows but never disappears. Always profile on representative hardware.

Index Design & Strategy
The single highest-impact optimization lever you have

Column Ordering in Composite Indexes

The most critical rule: put equality predicates first, then range predicates, then ORDER BY columns. This maximizes selectivity early in the B-tree traversal.

Suboptimal IndexBAD
-- Range column BEFORE equality column
-- Wastes the range scan entirely
CREATE INDEX idx_orders_bad
ON orders (created_at, status);

-- Query: must scan full created_at range
-- then filter status in heap
SELECT * FROM orders
WHERE status = 'pending'
  AND created_at > '2024-01-01';
Optimal IndexGOOD
-- Equality first → Range second
-- Planner narrows status=pending first
CREATE INDEX idx_orders_good
ON orders (status, created_at);

-- Seeks to status='pending' leaf block
-- then range-scans created_at forward
SELECT * FROM orders
WHERE status = 'pending'
  AND created_at > '2024-01-01';

Covering Indexes (Index-Only Scan)

PostgreSQL INCLUDE — Covering IndexBEST PRACTICE
-- Include projected columns to eliminate heap fetches entirely
-- status, user_id = search predicates → B-tree key columns
-- amount, created_at = SELECT columns → stored in leaf pages
CREATE INDEX idx_orders_covering
ON orders (status, user_id)
INCLUDE (amount, created_at);

-- This query now NEVER touches the heap table
SELECT amount, created_at
FROM   orders
WHERE  status  = 'shipped'
  AND  user_id = 42;

-- Verify with EXPLAIN:
-- → Index Only Scan using idx_orders_covering
-- → Heap Fetches: 0  ← target metric

Partial Indexes

Partial Index — Filter Nulls or Rare ValuesHIGH IMPACT
-- Index only rows where the predicate is true
-- 95% of orders are 'completed' — only index the 5% that are 'pending'
CREATE INDEX idx_orders_pending
ON orders (created_at)
WHERE status = 'pending';

-- Tiny index, faster updates, perfect cardinality for this query:
SELECT * FROM orders
WHERE status = 'pending'
ORDER BY created_at;

-- Another common pattern: index non-null columns
CREATE INDEX idx_users_email_notnull
ON users (email)
WHERE email IS NOT NULL;

Expression & Function Indexes

Index on ExpressionPATTERN
-- Problem: function on column = no index use
SELECT * FROM users
WHERE LOWER(email) = 'alice@example.com';
-- ↑ causes Seq Scan regardless of index on email

-- Fix: index the expression itself
CREATE INDEX idx_users_email_lower
ON users (LOWER(email));

-- Now the planner can use it.
-- Same pattern for date truncation:
CREATE INDEX idx_events_day
ON events (DATE_TRUNC('day', created_at));

-- MySQL equivalent: generated column
ALTER TABLE users
  ADD COLUMN email_lower VARCHAR(255)
  AS (LOWER(email)) STORED;
CREATE INDEX idx_email_lower ON users (email_lower);

Index Types

⚠ Index Overhead
Every index costs: extra storage, slower writes (INSERT/UPDATE/DELETE must maintain the index), and bloat over time. Unused indexes are pure overhead. Audit periodically with pg_stat_user_indexes and drop unused ones.

Anti-Patterns & Fixes
The most expensive mistakes engineers make daily

1 — Function Calls on Indexed Columns (Index Killer #1)

Anti-PatternKILLS INDEX
-- Any function on the left side = Seq Scan
WHERE YEAR(created_at) = 2024
WHERE LOWER(name) = 'alice'
WHERE CAST(user_id AS TEXT) = '42'
WHERE DATE(created_at) = '2024-03-01'
FixINDEX FRIENDLY
-- Push computation to the literal side
WHERE created_at >= '2024-01-01'
  AND created_at <  '2025-01-01'
-- OR use expression index (see §2)
WHERE LOWER(name) = 'alice' -- with expr idx
WHERE user_id = 42          -- fix type mismatch
WHERE created_at >= '2024-03-01'
  AND created_at <  '2024-03-02'

2 — Implicit Type Coercion

Type Mismatch — Silent Plan KillerDANGER
-- Schema: user_id BIGINT, but param is a string
-- MySQL silently casts and disables index
SELECT * FROM orders WHERE user_id = '100';  -- ← string

-- Schema: phone VARCHAR, but param is integer
SELECT * FROM users WHERE phone = 5551234567;  -- ← int

-- Fix: match exact types in application code & ORM
-- Verify with EXPLAIN that index scan is used
SELECT * FROM orders WHERE user_id = 100;    -- ← BIGINT
SELECT * FROM users  WHERE phone = '5551234567'; -- ← VARCHAR

3 — SELECT * in Production Queries

Anti-PatternBAD
-- Fetches all columns including BLOBs, JSON
-- Prevents covering index usage
-- Breaks when schema changes
SELECT * FROM products
WHERE category_id = 5;
FixGOOD
-- Project only what you need
-- Enables covering index (Index Only Scan)
-- Smaller network payload
SELECT id, name, price, stock
FROM   products
WHERE  category_id = 5;

4 — The N+1 Query Problem

N+1 → Batch with IN or JOINCRITICAL
-- Application code anti-pattern (pseudocode)
orders = query("SELECT * FROM orders WHERE status='pending'") -- 1 query
FOR EACH order IN orders:
    user = query("SELECT * FROM users WHERE id = " + order.user_id) -- N queries!

── Fix 1: JOIN ──────────────────────────────────────────────
SELECT o.id, o.amount, u.name, u.email
FROM   orders o
JOIN   users  u ON u.id = o.user_id
WHERE  o.status = 'pending';

── Fix 2: Batch IN (when JOIN is impractical) ────────────────
order_ids = [1, 2, 3, ...]  -- collect first
SELECT * FROM users
WHERE id IN (1, 2, 3, ...);   -- 1 query total

5 — LIKE with Leading Wildcard

Leading WildcardNO INDEX
-- Cannot use B-tree index
WHERE name LIKE '%alice%'
WHERE name LIKE '%son'
AlternativesUSE INSTEAD
-- Trailing wildcard: B-tree works
WHERE name LIKE 'alice%'

-- Full-text search (PostgreSQL)
WHERE to_tsvector('english', name)
    @@ to_tsquery('alice')

-- pg_trgm for arbitrary substring
CREATE INDEX idx_trgm ON t
  USING gin (name gin_trgm_ops);

6 — OR Conditions

OR → UNION ALL (often faster)PATTERN
-- OR often prevents optimal index use; forces bitmap scan merge
SELECT * FROM orders
WHERE status = 'pending'
   OR status = 'processing';

-- Better: use IN (equivalent for equality)
WHERE status IN ('pending', 'processing');

-- For cross-column OR, UNION ALL lets each branch use its own index
SELECT * FROM users WHERE email = 'a@b.com'
UNION ALL
SELECT * FROM users WHERE phone = '555-1234'
  AND email != 'a@b.com';  -- deduplicate overlap

JOIN Optimization
Join algorithms, ordering strategy, and when each wins
🔁
Nested Loop Join

Outer row × inner index lookup. Best when outer set is small and inner join column is indexed. O(n·log m).

Best small outer, indexed inner

🪣
Hash Join

Build a hash table from smaller relation, probe with larger. Excellent for large unsorted joins. O(n+m) with memory. Spills to disk if work_mem insufficient.

Best large equi-joins

🔀
Merge Join

Both inputs must be sorted on join key. Extremely fast when both sides pre-sorted (index scan). O((n+m)·log). Preferred when ORDER BY matches join key.

Best pre-sorted inputs

Join Column Data Types Must Match

Type Mismatch Causes Implicit Cast on JoinCOMMON BUG
-- orders.user_id  INT  vs  users.id  BIGINT
-- PostgreSQL will cast INT→BIGINT, may skip index
SELECT o.*, u.name
FROM   orders o
JOIN   users  u ON o.user_id = u.id;  -- ← silent cast

-- Check types:
SELECT column_name, data_type
FROM   information_schema.columns
WHERE  table_name IN ('orders', 'users')
  AND  column_name IN ('user_id', 'id');

Join Order — Filter Early

Drive From the Most Selective Table FirstSTRATEGY
-- Bad: joining large tables first, filtering late
SELECT p.name, c.name AS category, s.qty
FROM   products p               -- 10M rows
JOIN   stock    s ON s.product_id = p.id  -- 50M rows
JOIN   categories c ON c.id = p.category_id
WHERE  c.slug = 'electronics';  -- 200 rows

-- Good: pre-filter categories, drive from tiny result
SELECT p.name, c.name, s.qty
FROM   categories c              -- 200 rows after filter
JOIN   products p ON p.category_id = c.id
JOIN   stock    s ON s.product_id = p.id
WHERE  c.slug = 'electronics';

-- Or hint the planner (PG):
SET join_collapse_limit = 1;  -- follow query order exactly

Lateral Joins — Correlated Subquery Replacement

LATERAL — Top-N Per Group (PostgreSQL)ADVANCED
-- Get the 3 most recent orders per user — elegant & fast
SELECT u.id, u.name, o.id AS order_id, o.amount
FROM   users u
CROSS JOIN LATERAL (
    SELECT id, amount
    FROM   orders
    WHERE  user_id = u.id         -- references outer row
    ORDER BY created_at DESC
    LIMIT  3
) o;

-- Alternative: ROW_NUMBER() window function
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY user_id
    ORDER BY created_at DESC
  ) rn FROM orders
)
SELECT * FROM ranked WHERE rn <= 3;

Aggregation Tuning
GROUP BY, HAVING, and window function strategies

Filter Before Aggregating

Late FilterSLOW
-- Aggregates ALL orders first
-- then filters with HAVING
SELECT   user_id, SUM(amount)
FROM     orders
GROUP BY user_id
HAVING   SUM(amount) > 1000
  AND    status = 'completed';
Early FilterFAST
-- Filter rows BEFORE aggregation
-- Reduce input to GROUP BY dramatically
SELECT   user_id, SUM(amount)
FROM     orders
WHERE    status = 'completed'  -- ← WHERE
GROUP BY user_id
HAVING   SUM(amount) > 1000;

Window Functions vs Subqueries

Window Functions — Single Pass Over DataPREFER
── Running totals ─────────────────────────────────────────
SELECT
  id, amount, created_at,
  SUM(amount) OVER (
    PARTITION BY user_id
    ORDER BY     created_at
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total
FROM orders;

── Percent of total per group ─────────────────────────────
SELECT
  product_id, revenue,
  100.0 * revenue / SUM(revenue) OVER (
    PARTITION BY category_id
  ) AS pct_of_category
FROM sales;

── Lag/Lead — compare to previous row ────────────────────
SELECT
  date, revenue,
  LAG(revenue) OVER (ORDER BY date) AS prev_revenue,
  revenue - LAG(revenue) OVER (ORDER BY date) AS delta
FROM daily_revenue;

FILTER Clause — Conditional Aggregation

FILTER — Single Pass Multi-Aggregation (PG 9.4+)ELEGANT
-- Instead of multiple subqueries or CASE WHEN inside SUM
SELECT
  COUNT(*) AS total_orders,
  COUNT(*) FILTER (WHERE status = 'completed')  AS completed,
  COUNT(*) FILTER (WHERE status = 'cancelled')  AS cancelled,
  SUM(amount) FILTER (WHERE status = 'completed') AS revenue
FROM orders
WHERE created_at >= '2024-01-01';

-- MySQL equivalent: SUM(CASE WHEN ...)
SELECT
  SUM(CASE WHEN status='completed' THEN 1 ELSE 0 END) AS completed
FROM orders;

Subqueries, CTEs & Derived Tables
When to inline, when to materialize, and when to avoid

CTE Materialization Gotcha (PostgreSQL 12+)

CTE Fence — Force vs Allow InlinePG SPECIFIC
-- Pre-PG12: ALL CTEs were optimization fences (materialized)
-- PG12+: CTEs inlined by default unless they are:
--   - referenced more than once, OR
--   - marked MATERIALIZED explicitly

── Force materialization (cache expensive computation once) ──
WITH expensive_cte AS MATERIALIZED (
  SELECT user_id, SUM(amount) AS total
  FROM   orders
  GROUP BY user_id
)
SELECT u.name, c.total
FROM   users u
JOIN   expensive_cte c ON c.user_id = u.id;

── Force inlining (let planner optimize through it) ──────────
WITH my_filter AS NOT MATERIALIZED (
  SELECT * FROM orders WHERE status = 'pending'
)
SELECT * FROM my_filter WHERE amount > 100;

EXISTS vs IN vs JOIN

EXISTS Short-Circuits — Faster for "at least one" checksPATTERN
── Use EXISTS for existence check (stops at first match) ─────
SELECT u.*
FROM   users u
WHERE  EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id
    AND o.amount > 1000
);

── IN with large subquery can be slow — use JOIN instead ─────
-- Bad: IN with correlated subquery
WHERE user_id IN (
  SELECT id FROM premium_users WHERE tier = 'gold'
)

-- Better: JOIN (planner can choose hash join)
JOIN premium_users pu
  ON pu.id = u.id AND pu.tier = 'gold'

── NOT EXISTS is almost always faster than NOT IN ────────────
-- NOT IN returns no rows if subquery contains NULL!
WHERE NOT EXISTS (
  SELECT 1 FROM blacklist b
  WHERE b.user_id = u.id
);

Profiling Workflow
Systematic diagnosis: from symptom to root cause in minutes
Step 1 — Identify Slow Queries
Enable slow query log or query pg_stat_statements. Sort by total_time descending to find the queries worth optimizing (not just slowest single run).
Step 2 — EXPLAIN (no execution)
Get the plan the optimizer chose. Identify join types, scan types, and estimated rows. Spot misestimates (estimated vs actual).
Step 3 — EXPLAIN ANALYZE (with execution)
Execute the query and get actual row counts, actual time, and loop counts. The gap between estimated and actual rows is the key signal.
Step 4 — EXPLAIN (ANALYZE, BUFFERS)
Add buffer stats: shared hit = cache, shared read = disk I/O. High read count = missing index or poor cache hit rate.
Step 5 — Fix & Verify
Apply the fix (index, rewrite, stats update). Run EXPLAIN ANALYZE again and compare execution time and buffer hits. Always measure before/after.

Full Profiling CommandPostgreSQL
EXPLAIN (

  BUFFERS,       -- I/O stats
  FORMAT JSON,   -- for tools like explain.depesz.com

FROM   orders o

pg_stat_statements — Fleet-Wide Analysis

Find Top 10 Queries by Total TimeMONITORING

  LEFT(query, 80)             AS query_preview,
  calls,
  ROUND(total_exec_time::numeric, 2) AS total_ms,
  ROUND(mean_exec_time::numeric,  2) AS avg_ms,
  ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,

    SUM(total_exec_time) OVER(), 2) AS pct_total

LIMIT  10;

Advanced Techniques
Materialized views, query hints, connection pooling, and statistics

Materialized Views — Pre-compute Expensive Aggregates

Materialized View with Concurrent RefreshHIGH IMPACT
-- Create once; query many times at near-zero cost
CREATE MATERIALIZED VIEW mv_user_revenue AS
SELECT
  u.id, u.name, u.email,
  COUNT(o.id)  AS order_count,
  SUM(o.amount) AS total_revenue,
  MAX(o.created_at) AS last_order_at
FROM  users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name, u.email
WITH DATA;

-- Index the materialized view
CREATE INDEX ON mv_user_revenue (total_revenue DESC);

-- Refresh without locking reads (requires unique index)
CREATE UNIQUE INDEX ON mv_user_revenue (id);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_user_revenue;

-- Schedule via pg_cron:
SELECT cron.schedule('refresh-mv', '*/5 * * * *',
  'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_user_revenue');

Statistics Targets — Fix Misestimates

Increase Statistics for Skewed ColumnsTUNING
-- Default stats target = 100 (about 300 distinct values tracked)
-- Skewed columns (status, country_code) need more detail

-- Check current stats for a column:
SELECT attname, attstattarget
FROM   pg_attribute
WHERE  attrelid = 'orders'::regclass
  AND  attnum > 0;

-- Increase for a specific skewed column:
ALTER TABLE orders
  ALTER COLUMN status SET STATISTICS 500;

-- Force re-analysis:
ANALYZE orders (status);

-- Check most common values after:
SELECT most_common_vals, most_common_freqs
FROM   pg_stats
WHERE  tablename = 'orders'
  AND  attname   = 'status';

work_mem — Sort & Hash Join Tuning

work_mem — Prevent Disk SpillsCONFIG
-- Default work_mem = 4MB (too low for analytics)
-- Each sort/hash in a query can use this much
-- N parallel workers × M concurrent connections × work_mem
-- must fit in RAM → set per-session for analytics queries

-- Per-session (safe approach):
SET work_mem = '256MB';
SELECT ... -- your expensive analytics query
RESET work_mem;

-- Check for disk spills in explain output:
-- "Sort Method: external merge  Disk: 45MB"  ← increase work_mem
-- "Sort Method: quicksort  Memory: 128kB"   ← fits in memory ✓

-- For hash joins:
-- "Batches: 8  (originally 1)"  ← spilled to disk, need more work_mem

Table Partitioning
Partition pruning, range partitioning, and maintenance
Range Partitioning by Month (PostgreSQL)PATTERN
-- Declarative partitioning (PG 10+)
CREATE TABLE orders (
  id         BIGSERIAL,
  user_id    BIGINT       NOT NULL,
  amount     DECIMAL(12,2) NOT NULL,
  status     VARCHAR(20)  NOT NULL,
  created_at TIMESTAMPTZ  NOT NULL
) PARTITION BY RANGE (created_at);

-- Create monthly partitions
CREATE TABLE orders_2024_01
  PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE orders_2024_02
  PARTITION OF orders
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Each partition gets its own indexes
CREATE INDEX ON orders_2024_01 (user_id, created_at);

-- Partition pruning is automatic when filtering on partition key:
SELECT * FROM orders
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31';
-- → scans ONLY orders_2024_01, not all other partitions

-- Drop old partition instantly (vs DELETE taking minutes)
DROP TABLE orders_2022_01;  -- immediate, no vacuum needed
✓ Partitioning Benefits
Partition pruning can reduce scan scope by 99%+ for time-range queries. Dropping old data is instant (DROP TABLE). Per-partition VACUUM and ANALYZE run concurrently. Partition-wise aggregation and joins can parallelize across partitions.

Senior Engineer Checklist
Run this before every production query review
  • ✅SELECT only the columns you need — never SELECT *
  • ✅Filter with WHERE before aggregating; use HAVING only for post-aggregate filters
  • ✅No functions on left-hand side of WHERE predicates on indexed columns
  • ✅Types of join columns exactly match — no implicit casts
  • ✅Use EXISTS / NOT EXISTS instead of IN / NOT IN for existence checks
  • ✅LIMIT applied as early as possible, not on the outermost query wrapping a full scan
  • ✅Pagination uses keyset/cursor-based approach, not OFFSET on large tables
  • ✅Equality predicates before range predicates in composite index column order
  • ✅Covering index (INCLUDE) used for hot read paths — verify with "Heap Fetches: 0"
  • ✅Partial index used where predicate is low-cardinality (status, is_deleted)
  • ✅Expression index exists if applying function to indexed column
  • ✅Foreign key columns are indexed (especially on the many-side of relations)
  • ✅Unused indexes identified and dropped (check pg_stat_user_indexes.idx_scan = 0)
  • ✅Index bloat checked for high-churn tables (pg_stat_user_tables)
  • ✅EXPLAIN ANALYZE run on representative data, not dev/staging with tiny dataset
  • ✅Estimated vs actual row counts checked — large gaps indicate stale stats
  • ✅ANALYZE run after bulk data load or major table changes
  • ✅Buffers checked: high "shared read" vs "shared hit" ratio signals I/O issue
  • ✅No "external merge Disk" in sort steps — increase work_mem if needed
  • ✅Query measured before and after optimization with pg_stat_statements
  • ✅Load tested at realistic concurrency (not just single-threaded latency)
  • ✅Materialized view used for dashboards/reports that tolerate slight staleness
  • ✅Table partitioned by time if table exceeds 100M rows with time-range access patterns
  • ✅Read replicas used for analytical queries to isolate from OLTP workload
  • ✅Connection pool configured (PgBouncer / ProxySQL) — not direct connections
  • ✅max_connections and pool size sized for CPU core count, not arbitrary
  • ✅Long-running transactions identified and minimized (they block VACUUM)
  • ✅VACUUM autovacuum settings tuned for high-churn tables

Keyset Pagination — Replacing OFFSET

OFFSET PaginationO(N) SCAN
-- OFFSET 1000000 still scans 1M rows
-- Gets slower with every page
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT  20
OFFSET 1000000;
Keyset PaginationO(1) SEEK
-- Pass the last seen cursor value
-- Seeks directly via index, always fast
SELECT * FROM orders
WHERE  created_at < '2024-06-15T10:23:00Z'
ORDER BY created_at DESC
LIMIT  20;
